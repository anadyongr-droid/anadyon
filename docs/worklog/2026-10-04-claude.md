**Last verified:** 4 October 2026, Claude.

## The second fingerprint run found a defect in the checking mechanism itself

The 06:00 reminder's first item was to read the overnight run. Two findings, and
the second is the one that matters.

### The cron fires, five and a half hours late — W43 answered

Run 2 is an `event: schedule` run that **started at 05:40:42 UTC against a 00:10
schedule**. So the schedule works and GitHub's lag is far larger than
"may be delayed" suggests. Last night's conclusion that it had not fired was
correct at the time and wrong as a prediction.

**It changes what the word *nightly* can promise.** A heartbeat must look for *a*
run in the last day, not a run at a time — and the lag is itself the reason a
heartbeat is needed, because a late run and no run are indistinguishable without
one. The mechanism is unchanged: one dated counts object per run in R2, so a
missing date is a missing night. Still to build, and the trap still stands:
**alert on a gap, never on success.**

### W44: the marker absorbed a finding it did not cause

Every one of W42's `quotes` rows came back annotated **`declared as quotes`**.

Migration 047's expected-change marker names six tables, because it grants
privileges on them — `quotes` among them. `explainWith` absorbed any change whose
object merely *started* with a declared name, so **a declaration about grants
explained twelve column differences and a policy**, by a migration that has
nothing to do with them and **has not been applied**.

**This is the design's central risk realised, in the dangerous direction.** A
marker that cries wolf gets muted and somebody notices. A marker that absorbs
what it did not cause makes the check **lie**, and the report still looks
attentive — which is why I would not have found this by reading it. The run
found it.

Child matching now covers only the **mechanical byproducts** of creating an
object: an index or a trigger, the primary key nobody writing a marker would
think to list. A column, a policy or a grant is a deliberate, declarable thing —
if a migration changes one, its marker can name it. The substring rule
(`name.includes(object)`) is **gone entirely**; it was never justified and could
absorb almost anything. Both halves were watched failing against the old rule
before the fix was trusted.

**Kept on the open list as closed rather than deleted,** because the reusable
part is not the fix: this mechanism was designed with Codex, reviewed by Fable,
tested twelve ways, and **still took one real run against production to expose**.
Three readers and a test suite did not substitute for using it once.

### Then two more defects in the same mechanism, from reading two rows — W45, W46

The marker still absorbed two rows, and writing the entry above required saying
*which* two. That is where both of these came from; neither was found by reading
code.

**W45 — the check could not see the migration it was holding a marker for.**
`production-fingerprint.sql` reads grants through an allow-list of grantees and
`anadyon_audit` was not in it. So migration 047's six grants — the mechanism
that tells `pgaudit` which objects to watch — were invisible on **both** sides
of the comparison. Once 047 is applied, those grants could be revoked in
production and no run would say a word: the rows would simply be absent, and
absence is the one thing a diff cannot report. The marker in force was declaring
a change the check was structurally incapable of seeing.

The allow-list stays, because naming production's dozen platform roles would put
a grant row for each on every table of every run — present on one side, absent
from the other by construction, which is the noise that gets a check muted. The
rot is caught instead: the test suite now reads every `create role` in
`supabase/migrations/` and fails naming any role the SQL does not read. Watched
failing with the role removed; the replayed side verified to carry all six grant
rows.

**W46 — a marker naming a table absorbed a grant to any role on it.** The two
`explained` rows turned out to be `service_role` grants on
`booking_email_deliveries` and `booking_email_events` — the Data API residue
migration 046 closes, nothing to do with 047, absorbed because 047's marker names
those tables (it grants to `anadyon_audit` on them). Only `normal` severity was
masked, so nothing was lost, **and that is the reason to fix it rather than
shrug**: the identical mechanism at `high` was W44, four hours earlier.
`explainWith` now absorbs a grant only when the marker names both the table and
the grantee. 047's marker already names the role, so the requirement costs an
author nothing and makes a grant declaration say *who*, not merely *where*.
Watched failing against the old rule.

### What this cannot close — W47

The fingerprint will now notice `pgaudit`'s **object list** being revoked. It
reads no settings at all, so `alter database … set pgaudit.role` being unset, or
`pgaudit.log` cleared on a role, stays invisible — which is exactly what a
project reset, a restore or a plan change would do, silently, leaving the
extension and the grants in place. An audit that is off while looking installed
is the inert control this project has produced four times.

It cannot be built yet: PGlite has no `pg_db_role_setting` row for it either, so
the expected side would read empty and the check would fire every night against a
correct database. Opened as W47, blocked on 047 reaching production.

## Codex's second review, audited finding by finding

Six high-severity findings and four operational ones, relayed by Tasos with
authorisation to correct and test. **All six upheld; one mis-stated in a way
that mattered, and the correction made it worse rather than smaller.** Every fix
was watched failing against the old code first.

**The pattern across all of them is one thing:** not one was a wrong answer. All
six were a **missing** answer — and a check that returns nothing looks exactly
like a check that found nothing. Three readers and 29 tests did not find these;
probing the running thing did.

### The `PUBLIC` grant finding, corrected upward

Codex reported that `information_schema.role_table_grants` omits `PUBLIC`,
citing PostgreSQL's note that the view *"omits tables that have been made
accessible to the current user by way of a grant to `PUBLIC`"*, and proposed
`table_privileges` instead.

**Checked both ways.** A `grant select to public` issued by the connected role
*does* appear, fired in a replayed database. But the documented scope of both
views is *"where the grantor or grantee is a currently enabled role"* — so
`table_privileges`, the proposed replacement, is scoped identically and would
have fixed nothing. **The real defect is broader and lands squarely on us:** the
nightly check connects as `postgres`, which on Supabase is **not** a superuser
(`rolsuper = false`, read from production 3 October) — so a grant issued from the
dashboard as `supabase_admin` was invisible, whoever held it. That is the exact
path the fingerprint exists to watch.

Reproduced before fixing: as a non-superuser role, `information_schema` returns
**nothing** for a grant the ACL shows plainly. Grants now come from
`pg_class.relacl` through `aclexplode`. The probe is now a test.

And the allow-list has a backstop: a new `grantees` section names any role
holding privileges on a `public` table that the six named roles do not cover —
one row per role rather than 29 per table, because the question *who is this and
why can it read a customer table* is answerable from the name alone.

### The four that were plain holes

- **Existence-only comparison.** `views` and `functions` were matched by name, so
  Codex flipped an existing function to `security definer` and the report stayed
  silent. **The largest blind spot found in this check so far**: a view is a
  stored select statement, so widening one exposes a column with no new object to
  notice. Definitions are now collected and compared, with whitespace normalised.
- **No marker validation at runtime.** The runner used every file in
  `supabase/expected-changes/` without calling `validateExpectedChange` once. An
  applied marker is the sharp case: the migration is then in production *and* in
  the replay, so nothing is left for it to explain, and it can only absorb
  somebody else's change — forever, since nothing retired it.
- **Markers named objects, not kinds.** W44 and W46's root rather than their
  symptom. `expected_kinds` is now required and binds byproducts too — the one
  shape the morning's narrowing left open was a grant declaration absorbing a
  genuinely missing index on a table it names, which is only not what happened to
  `quote_rate_limits_blocked_idx` because 047's marker does not name that table.
- **`authenticated` treated as noise.** The rule was written about Supabase's
  `service_role` defaults and applied to every role but `anon`. On a Supabase
  project `authenticated` is any holder of a valid JWT. Now `critical`, and it
  cannot cry wolf: a grant the migrations make appears on both sides and produces
  no row.

### The notification path — E21's defect in a second place

Telegram was gated on `steps.compare.outcome == 'failure'` alone, so a missing
`SUPABASE_DB_URL` or a failed production query — both of which fail the job
*before* the comparison — sent nothing. **The check went silent in exactly the
circumstances where it had stopped checking.** Now `failure() ||
steps.compare.outcome == 'failure'`, with a headline for the case where there is
no report to quote.

### One decision taken rather than asked

Definition differences are classified `normal`, not `high`, and that is
deliberate and dated. The replay runs **PostgreSQL 18.3** (PGlite 0.5.8) and
production is **17.6** (recorded 19 August). `pg_get_viewdef` and
`pg_get_functiondef` re-render a parse tree, and two major versions may render
the same object differently — which at `high` would be a permanent red for one
view and 34 functions. The first run measures it; W49 holds the decision and the
larger question it raises, which is whether `format_type` also disagrees, since
that is how every column type in this comparison is read — and twelve of W42's
findings are column types.

`MAINTAIN` is excluded from the privilege list for the same reason: it arrived in
17, and the replay showed it on every table while `information_schema` never
reported it at all.

## W42 answered — and the answer was already in the repository

Tasos chose route 2 — "production is right and the baseline never ran" — and it
is correct. **`001_baseline.sql` was never run against production.**

The evidence needed no production access: `supabase/schema.sql` creates five
tables and **no `quotes`**; the root `supabase-migration.sql` runs `ALTER TABLE
quotes ADD COLUMN IF NOT EXISTS …` and never creates it; and **migration
`010_close_schema_drift.sql` says it outright in its own header**, on 15 August —
*"The baseline declares columns the live database never received."* The baseline
has declared the missing index and `pickup_date date NOT NULL` since 15 August
against a database that has never had either.

**§9, a third time this week.** The answer to the question I was asked to
investigate was sitting in a migration header, in this repository, since August.
The investigation worth having was not "what happened" but "why did 010 not
finish it", and that answer is mechanical: `ALTER TABLE … ADD COLUMN IF NOT
EXISTS` can only add a missing column. It cannot change a type, cannot add `not
null`, and says nothing about an index. **A reconciliation script written with
`IF NOT EXISTS` everywhere converges on presence and never on shape** — three
times now in this project.

Written up in `MIGRATION-REPLAY-RESULT-2026-08-30.md`, which already owned the
subject, rather than in a new document.

**And the undeclared `Service role only` policy appears nowhere in `supabase/`.**
That is Supabase's dashboard naming: it was created through the dashboard,
outside every control this project has. It blocks rather than exposes, so it is
not an incident — it is proof that the thing the fingerprint was built to detect
does happen.

**What I did not do, and would not:** edit the baseline to match production so
the check goes quiet. Twelve questions would become zero by fiat, and the one
control that can see production would be silenced by the first thing it found.
The twelve columns are read from the next run's report — not from this
transcript, per §8 — and then decided one at a time.

`npm run verify:fast` after all of it: **142 files, 1653 tests, green.**

## The first run whose rows I could read — 37189919105

Three things came out of it, and the first was a defect in the thing I had just
built.

**The `normal` group was truncated after one row.** A `function.definition`
difference carries both function bodies — some three thousand characters — and it
ate the whole annotation budget, so twelve rows were dropped with an honest "and
12 more row(s)". The twelve were the ones worth reading. Each row is now capped
at 300 characters: **the annotation is an index of findings, and a function body
is not a finding.** Measured, not anticipated, like everything else today.

**W42's twelve columns, and they are three classes rather than twelve problems.**
Six money columns lost their scale (`numeric(10,2)` declared, bare `numeric`
held). Two date columns are `text` and nullable — the class with a consequence
outside the database, since `lib/aadeXml.ts` puts `pickup_date` straight into
`<issueDate>` for AADE. Four lost `not null`, which §4 names as the minimum to
save a reservation. And the policy in full: `to public`, command `*`,
`using (false)` — a deny-all policy, the belt beside §6's braces,
dashboard-created and declared nowhere.

**I did not write the tightening migration, and that is the decision.** It would
fail halfway through on live data in the SQL editor — `type date` raises on the
first unparseable row, `set not null` on the first null, `numeric(10,2)` on a
value too large — and each failure leaves the earlier statements applied and the
rest not. `scripts/sql/quotes-drift-diagnostic.sql` answers it in three rows,
writes nothing, and is paste-ready; migration 048 gets written against what is
actually there.

**W49(b), half answered.** The `function.definition` row is **not** a deparser
artifact: Postgres stores a body verbatim, and the difference is two comment
lines present in the migration and absent from production's copy. The code is
identical. So that comment was added to the migration *after* it was pasted — the
same shape as W42, and cosmetic. What remains unmeasured is whether any *other*
definition row is a version artifact, because twelve rows were cut. W52 is the
change that would make a definition difference mean something: strip comments
with a quote-aware stripper, then promote to `high`. **Order matters and is
written down** — read one full run's rows before normalising the evidence away.
