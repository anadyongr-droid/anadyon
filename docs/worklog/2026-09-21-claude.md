### A verification trap worth not falling into twice

`v4.38.1` is an **annotated** tag, and that changes what a lookup returns:

```
c23de5a82f64bb08c6d9f28844551440ca298e76    refs/tags/v4.38.1
1c5b675653bb5c22dbe9b12b556ec555138e09fd    refs/tags/v4.38.1^{}
```

The first is the tag object; the second is the commit, and the commit is what a
workflow pins. An exact-ref query for `refs/tags/v4.38.1` returns **only the
first** — which looks exactly like Dependabot proposing a SHA that disagrees
with the tag, the precise shape of a supply-chain red flag, when nothing is
wrong. I very nearly reported it as one.

Yesterday's v4.37.9 check happened to use a pattern matching both lines, so the
distinction never came up. **Peel the tag before concluding anything from a
mismatch.**

## E16 diagnosed: the secret begins `postpostgresql://`

Two wrong guesses preceded the measurement, and both cost a round trip.

First percent-encoding — Tasos replied that the password has no special
characters. Then a shape report that said `scheme: MISSING or wrong` without
saying which, so it identified the fault but not the fix.

`describeDatabaseUrlShape` (#159, #160) now names it from the run itself:

```
  scheme: "postpostgresql://" — WRONG, expected postgresql:// or postgres://
```

**Everything else about the value is correct**, which is exactly why it looked
mysterious: a 14-character alphanumeric password, a `supabase.com` pooler host,
port 5432, path `/postgres`, one `@`, no whitespace, no quotes, no leftover
placeholder. Four extra characters on the front, and the CLI rejects the whole
string before it ever tries to authenticate.

The fix is to delete the leading `post`. Only Tasos can do it.

**The lesson is the one the project already holds.** A secret nobody can read
back cannot be diagnosed by guessing at it, and two guesses is two more than
the evidence supported. The instrument should have been built first —
`AGENTS.md` says a reproduction must be able to reproduce, and "try
percent-encoding" was not a reproduction of anything.

A small coincidence worth recording: `tests/schemaParity.test.ts` already
carried `postpostgresql://…` as its malformed-URL fixture, written before any
of this. The failure mode was anticipated in a test and still took three
attempts to recognise in the wild.

## I said the Telegram alert fired. It never has.

Tasos asked me to double-check, having received no Telegram alert since the
move off Make.com. He was right and I was wrong, and the way I was wrong is the
one this repository keeps turning up: **I read a green step as evidence of the
thing the step is supposed to do.**

The old step could report success in two ways while delivering nothing —
`[ -z "${TELEGRAM_BOT_TOKEN:-}" ] && exit 0`, which exits 0 on a missing token,
and `curl -s ... > /dev/null`, which has no `--fail` and discards an answer that
Telegram returns as HTTP 200 with `{"ok":false}` for a bad chat id.

**`lib/telegram.ts` already had every part of this right.** Its comment names
the same three faults and says outright that a 200 is not a delivery. The fix
never reached the workflow, so the application path was sound and the
operational one was not — a fix applied where it was noticed rather than
everywhere it applied.

### The lesson, which is not a new one

Three times in two days a green check has meant nothing: the workflow that
*contained* the right command but could not run it (#146), the test that
sampled a list it was meant to guard (#144), and now an alert that exits 0
when it cannot send. **An alert path nobody exercises is not an alert path** —
the only way to learn this one had failed was to need it, and then it failed
silently. That is why the test workflow exists rather than only the fix.

## Asked whether the alert test covers anything else. It does not, and that is the finding.

`alert-test.yml` exercises Telegram and only Telegram. But tracing what depends
on Telegram turned up something larger.

`app/api/cron/morning-briefing/route.ts`:

```
reportHealth() → runHealthChecks() → formatHealthAlert() → sendTelegram(alert)
```

That is the **only** delivery. All six checks in `lib/healthChecks.ts` — each
one drawn from a real incident, per its own header — are invisible unless
Telegram works: analytics reachable past the CSP, the Resend webhook accepting
events, the rate card readable, admin accounts having roles, **recent database
backup**, and mail DNS hardening.

**The backup gap had two independent detectors and both were mute.** The
workflow's own alert (E17 — the secrets do not exist) and `checkBackupFreshness`,
which exists precisely to catch a stale backup and whose only outlet is the
channel that was not delivering. Two detectors, one channel, no verification of
the channel.

**The gap is that health results have no pull-based surface.** If Telegram is
down you learn nothing — including that Telegram is down. Recorded as **E18**
with a proposed remedy rather than built, since it needs a decision about where
that surface lives.

**Email is the model and is in better shape**: `lib/mailer.ts` checks its
result and queues failures to `alert_outbox`, and `npm run test:mail` exercises
it live on demand. Both halves — verify, and be exercisable — which is what
Telegram was missing.

The general shape, worth carrying beyond this project: **a monitoring system
needs somewhere to look, not only something that tells you.** Push-only
monitoring fails closed and silent, and its failure mode is indistinguishable
from everything being fine.
