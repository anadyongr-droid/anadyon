### W26 closed — and the audit had understated it

`lib/filingBacklog.ts`, `app/api/admin/aade/backlog/route.ts` and a banner plus
per-row sentence on the reservations screen. 35 tests, six mutations run and
watched.

**The finding worth keeping: `dcl_status = 'submitting'` is a third state, and it
is unrecoverable.** `claim_dcl_submission` refuses to re-claim anything already
`submitting`, so such a reservation answers 409 on *every* retry, for ever.
Yesterday's W27 fix stopped a slow socket creating new ones, but it could not
recover rows already in that state, and **no screen anywhere showed them.** The
backlog separates the two states because they need different instructions: an
`error` row can be retried; a `submitting` row has to be reset first, and sending
someone to a button that answers 409 is worse than saying nothing at all.

Two other decisions:

- **The clock is the pick-up date, not the attempt time.** No `dcl_attempted_at`
  column exists and none is needed — the Digital Client List declares a *rental*,
  so the deadline belongs to the rental. A rental already running with no filing
  is overdue now. A rental starting *today* is deliberately "imminent" rather than
  "overdue", because the declaration is due at the start and calling it late on
  the day it begins would cry wolf.
- **It has its own query, and that is the substance.** The reservations list
  orders by `created_at` descending with no explicit limit, so PostgREST returns a
  *window* — and the oldest failed filing is exactly the row that falls off it. A
  count over that list would report a confident "3 outstanding" while an August
  rental sat unfiled outside the window. The route filters in the database, orders
  oldest pick-up first, caps its response and **says when the cap was hit.**

**Not built, deliberately:** resubmission. A filing abandoned on W27's timeout
records `error` but may have been accepted by AADE with the answer lost, so a
retry can file a **duplicate** statutory declaration — worse than filing late. The
wording sends the operator to AADE's own record first. Whether an unknown filing
is retried automatically or only after a human checks the portal changes what
staff must do, so that rule is Tasos's under §13.

## The PGlite "flake" was a ten-second budget, and it is measured now

**Earlier today I called this "not a defect". That was wrong**, and I said so
before fixing it: a gate that fails two runs in eight is an engineering
reliability defect even when no customer is affected. What I had not done was
measure it, so I did that first.

**The measurement, on this four-core container.** Booting one PGlite and running
`select 1` costs **1.9s**. The cost scales with simultaneous boots, because WASM
initialisation is CPU-bound and there are four cores:

| Concurrent boots | slowest |
|---|---|
| 1 | 1.9s |
| 4 | 5.9s |
| 8 | **11.7s** |
| 14 | **21.3s** |

Vitest's default hook budget is **10s**, so it is crossed at about seven
simultaneous boots — before the hook has replayed a single migration.

**Reproduced, not inferred.** `--maxWorkers=14` over the fourteen PGlite files
failed four to six of them, every hook failure reading `Hook timed out in
10000ms`. `AGENTS.md` requires a reproduction that can actually reproduce, and
this one does, on demand.

**The evidence for the diagnosis was already in the repo.** Two of the fourteen
carried a hand-set budget — `openDamageView` 30s, `rentalHandovers` 60s — and
those two never failed. Someone hit the timeout on each, raised that file's
number, and moved on. A file with its own budget stops failing and therefore
stops reporting, which is precisely how the remaining hooks stayed on the
default with nothing pointing at them.

**The fix is one number.** `hookTimeout: 60_000` in `vitest.config.ts`, the two
per-file budgets removed, and `lib/pgliteHookBudget.test.ts` holding it there.
At the same forced fourteen-way contention that failed four files, all fifteen
files and 204 tests now pass; the full suite ran clean three times in a row, and
`verify:fast` is green at 133 files / 1516 tests.

**Two corrections I made to my own work mid-task, both worth recording.** The
first draft of the guard test **counted itself** — it detects `new PGlite(` and
mentions that string in its own prose, so it reported fifteen files. The second
and worse one: it matched `}, 20_000)` at the start of a line and flagged
`atomicBookingMigration`, whose 20s is the timeout of a single `it` and not a
hook budget at all. Conflating the two would have had me delete a legitimate
test timeout. The rewritten test does parenthesis-balanced extraction of each
hook call, skipping quotes so a `)` inside SQL does not unbalance it, and it
**asserts the distinction** rather than relying on me having got the regex right.

**And one claim of mine that went stale within the hour.** I wrote in the config
comment that the `atomicBookingMigration` test timeout was "observed once and not
reproduced". It then reproduced on the next forced run — two of three. Corrected
in place rather than left standing: that file now carries 60s with its reasoning,
and `testTimeout` stays at its default, because raising it globally would weaken
fifteen hundred fast tests to cover one.

**What I deliberately did not do, now W28.** Eight files do their setup inside a
test body, so no shared hook budget can reach them, and three boot in
`beforeEach` — about **ninety nine** boots between `checkInFinalisation` (33),
`checkOutFinalisation` (37) and `handoverCorrectionAndVoid` (29). Sharing an
instance is a large saving on wall time, but every one of those tests currently
gets a virgin database and trading that isolation away needs the replacement
*proved* equivalent, not assumed. That is a deliberate change, not a timeout fix.

## What this session can actually reach, tested rather than assumed

Written up as **W29**, because Codex's access proposal rests on assumptions about
this environment that turn out to be wrong in both directions.

**Every service API is reachable from here.** `api.supabase.com` → `401`, both
project hosts → `401 No API key found`, `api.vercel.com` → its own `403
missingToken`, `sentry.io/api/0` → `401`. Each of those means *reachable,
credential absent*. My earlier claim that dashboards are unusable here is true
only of the **browser** — Chromium fails `ERR_CERT_AUTHORITY_INVALID` and the CA
install was refused — and I had generalised from the browser to the service. **A
read-only token is the shape that works, and no browser profile is needed.**

**But some GitHub paths are blocked by the session proxy, and no token fixes
those.** There are two distinct 403s and they mean opposite things:

| Message | From | A fine-grained PAT helps? |
|---|---|---|
| `Resource not accessible by integration` | GitHub | **Yes** — branch protection, code-scanning alerts, Dependabot alerts |
| `Access to this GitHub API path is not permitted through this proxy` | the harness | **No** — `collaborators`, `environments`, `actions/secrets`, `actions/permissions`, `secret-scanning/alerts`, `vulnerability-alerts` |

Anything in the second row has to be pasted by a person however the credentials
are arranged, so it should not be on anyone's list of things a token will solve.

**The credential position is unchanged and deliberate.** No Supabase, Vercel,
Sentry, Stripe, Resend or Apify credential exists in this container; the only
tokens are GitHub's and the session's own, and there is no `.env` file at all.
That is the boundary `AGENTS.md` says is the one that actually holds, and the
request in W29 is for read-only tokens that keep it — explicitly **not** the
production service-role key. `read_only` protects integrity, not confidentiality:
a read-only token over production still reads customer rows, which is the thing
§6 exists to prevent, so staging `fzycvstifmltxybffinq` is the default target and
production reads are confined to `pg_catalog` and `information_schema`.

**One practical detail worth writing down:** a token added to the environment
takes effect in the **next** session, not the one that asked for it.
