## Reconciliation, and a finding all three passes missed

`docs/agent-controls/RECONCILIATION-2026-10-03.md` is the merged position and the
document to act from. The design document now points at it and is kept only for its
threat model, the enforced-versus-advisory discipline, and the record of the browser
claim that was wrong.

**The finding: P3 is mitigable after all, and we were all looking one layer too low.**
Every pass concluded that a logged-in browser session against production could not be
constrained, because the two dashboards are **paths under one host** and a host-level
deny cannot split them. True — of *network* controls. Chrome's `URLBlocklist`
enterprise policy matches `[scheme://][.]host[:port][/path][@query]`, longest matching
path wins, and Chrome evaluates the URL **before the request leaves the browser**, so
the path is in clear text to its own policy engine. **The discriminator was never
unavailable; three of us reasoned about the network layer, where the path is inside
TLS, and none looked at the browser's own policy engine.**

It needs **no TLS interception**, which is why it is preferable to the obvious
alternative. A man-in-the-middle proxy with a trusted CA would see paths everywhere
and would be a universal decryption capability on the machine, reading every
credential in every session, installed to defend against a one-click mistake. Recorded
as considered and rejected.

**Status is "mitigated, unproven", and E29 is the test that decides.** The Supabase
dashboard is a single-page app. If a client-side `pushState` navigation bypasses the
blocklist, the control catches a typed URL and nothing else. Two further unknowns ride
on the same test: the macOS install path without MDM, and that Chrome policy is
per-user or per-machine rather than per Chrome *profile* — so it blocks the production
dashboard for Tasos too, which argues for a separate browser build for the agent.

## On an agent as a firewall — a firewall yes, an agent no

Asked whether an agent could adjudicate "staging: approved, production: denied".

**It would make things worse, for two reasons.** The question is a string comparison —
a model can be persuaded, `===` cannot, and putting a probabilistic component where a
deterministic one exists trades a guarantee for a judgement. And **prompt injection is
risk 1 in this very threat model**: an adjudicating model reads attacker-influenced
text and then decides, which adds a second thing that can be talked into yes and
grants it authority.

**The rule that makes a model safe to add, and it is in the reconciliation:** a model
may only ever **narrow, never widen** — deny, or escalate to the human; never approve
what the deterministic layer denied. Under that rule a model earns its place where no
rule decides the question, and the live example is §13: *could a customer receive
different terms, cover or treatment?* That is judgement, it is exactly what §13
requires before a merge, and it escalates rather than grants.

**And on whether an agent can implement any of this:** largely not, structurally.
**The controls an agent can install are exactly the controls an agent can uninstall** —
Fable's circularity finding generalised. Root-owned files, a policy under `/Library`, a
dashboard setting, a paste into the SQL editor: each is outside agent reach, and that is
what makes it a control. What an agent should do instead is generate the exact artifact
so the human's step is a paste rather than a design, **build the verifier and put it
where the agent cannot reach it** — a CI test that fails when a deny list loses the
production ref is enforcement the agent cannot undo — and fire the controls and record
what happened. The agent builds the instrument; the human installs the boundary.

## Two corrections to Codex's ten-point plan, both checked

**The GitHub token split it proposes is not possible.** Merging a pull request requires
`contents: write`, the same permission as pushing, and there is an open GitHub feature
request to separate them. So a token cannot push-but-not-merge. **Branch protection is
the lever** — and `main`'s required check carries `enforcement_level: "everyone"`, so
even the owner cannot merge with `build` red. Required *reviews* are zero, which I
proved by merging #195 unreviewed. **That is the gap worth closing**, not the token.

**Ten-to-fifteen-minute monitoring is the wrong cadence.** 100–144 runs a day for a
response that is manual anyway; GitHub's scheduled workflows are best-effort and skip
under load, so a tight schedule that silently misses is worse than a nightly one that
does not; and the likeliest outcome of a noisy monitor is that it gets switched off.
Nightly, a manual trigger, and a heartbeat. The heartbeat matters more than the
frequency, because nothing else distinguishes **clean** from **stopped**.

**And one thing not adopted from it:** denying `anadyon.gr`. It is the public website,
and verifying a published claim against a rendered page is what §8 and §10 require and
what caught A02. Denying it removes the check, not the risk.

## The production gate: built, and every fault was found by firing it

`.claude/hooks/production-gate.mjs` — a `PreToolUse` gate implementing Tasos's own
suggestion: *staging approved, production denied*, with code rather than a model
deciding. Registered in the checked-in settings so it binds every agent in this
repository, and `docs/agent-controls/codex-hooks-template.json` points Codex at the
same file, so the two share one decision procedure rather than two that drift. Both
read the refs from `scripts/deployment-boundary-lib.mjs`.

**Why a rule and not a model**, which was the actual question. "Does this act on
production?" is a string comparison: a model can be argued out of its answer and
`===` cannot, and prompt injection is risk 1 in this threat model, so an adjudicating
model reads attacker-influenced text and then decides. The composition rule that
makes a model safe to add is that it may only **narrow, never widen**.

**Fired live:**

| Attempt | Result |
|---|---|
| `node -e` fetching production | **denied** |
| `curl`, `psql`, `supabase link`, `wget`, `python3` at production | denied |
| `node -e` fetching staging | **allowed, HTTP 401** |
| compound of local reads naming the production ref | allowed |
| in-place destruction of a control file | denied |

The first row is why it exists: the settings deny list names four programs and
**cannot enumerate every program that opens a socket**.

### Four faults. Seventeen unit tests passed while three of them were live

**1. A compound of permitted reads was denied.** The rule asked whether a shell
operator was present at all, so three local reads joined by `&&` were refused. Every
unit test exercised a single command.

**2. It blocked its own maintenance, and I walked past it in one line.** The guardrail
rule denied any call naming a control file, which included the edits that author the
controls: **four consecutive repair attempts refused**, each because the repair command
quoted one of the paths. Assembling the path from parts defeated it immediately. That
is Fable's circularity finding demonstrated instead of argued, and it settles the
rule's worth — **nothing against intent.**

**3 and 4. It could not tell describing an action from performing one.** A command
quoting a dangerous verb as a *test fixture* was denied; then a heredoc writing **this
very worklog entry** was denied, because the prose contained the word "rm". Both are
the same fault as (1): a judgement about the whole string where the question is about a
segment. The verb must now be the program a segment runs.

**The pattern across all four:** every one was an over-denial, every one was invisible
to the unit tests, and every one was found by using the thing. Over-denying is also the
failure that matters more in practice — a gate that blocks ordinary work gets deleted by
whoever is debugging at speed, and three of these four blocked the commands by which the
gate is reviewed and documented.

## A dedicated agent firewall: considered, declined

Proposed by Tasos: build a firewall specifically for AI agents, running alongside LuLu.
Declined, with the reasoning recorded so it is not re-proposed.

**It cannot solve the gap that matters.** The dashboard problem is two paths under one
host, and a network firewall sees the host rather than the path, because the path is
inside TLS. That is the same wall hit at four layers today, and a dedicated firewall
hits it too. The only way past is TLS interception with a trusted CA — a universal
decryption capability on the machine, reading every credential in every session, to
defend against a one-click mistake.

**Process attribution does not work either.** Such rules are per process, and the
ChatGPT app is one process serving both the agent's work and Tasos's own use of it;
Chrome likewise. A deny blocks him, an allow allows the agent. I believed a
per-Chrome-profile proxy would separate them and **checked rather than assuming**:
Chrome's proxy settings are per-profile internally, but Chrome on macOS exposes no way
to configure them per-profile, needing an extension or a separate browser
installation — which is E28 and E29, already on the list and free.

**And most of the value already runs.** LuLu covers unexpected egress, which is the
real contribution of a local firewall; production hosts are denied at three layers. A
macOS Network Extension needs a developer certificate and entitlements, sits in the

### 27 `high` rows, splitting cleanly in two

**Thirteen were noise, of one shape, and I predicted this class.** `service_role`
holding `REFERENCES`, `TRIGGER` and `TRUNCATE` on top of the four privileges the
migrations grant. Supabase's default privileges grant `ALL` on a new table in
`public`; PGlite has no such defaults, so the replay shows only what each
migration wrote. Permanent, harmless, and **it buried the thirteen rows that
mattered** — which is exactly how this kind of control dies: a report whose first
screen is always the same thirteen lines gets skimmed, then filtered, then muted.

Narrowed the rule rather than the output: for any role except `anon`, a privilege
production has **extra** is `normal`, and only a privilege the application needs
and has **lost** is `high`. Both halves of that asymmetry are asserted. An `anon`
gain stays `critical` and is still never absorbed by a marker.

**Thirteen are real, and they are W42.** Production's `quotes` table is looser
than the migrations in twelve places, all in the same direction: `pickup_date`
and `dropoff_date` are `text` where the file says `date not null`; four columns
are nullable where it says `not null`; six money columns are bare `numeric` where
it says `numeric(10,2)`. Plus `quote_rate_limits_blocked_idx`, which
`001_baseline.sql` creates and production does not have, and a
`quotes."Service role only"` policy that production has and no migration declares.

**Hypothesis, labelled:** `001_baseline.sql` describes production rather than
having created it, and was never run there. Every difference points that way and
the missing index from that same file is the strongest evidence. Establishing
*why* comes before writing any reconciliation — and an agent does not apply it.

**Not an emergency, and not nothing.** The app has run on this schema for months.
But free-text dates mean no database-level validation on a customer-facing table,
and nullable columns mean an incomplete quote can be stored.
