## Supabase removes the automatic Data API grant on 30 October

Tasos forwarded the notification email. **Verified against Supabase's own
documentation before acting on it**, per §8 and because a pasted email is not a
primary source: `supabase.com/docs/guides/api/securing-your-api` says it
outright — *"Supabase is changing the platform default to revoke these
automatic grants so that exposure becomes opt-in."* The doc page carries no
date; the 30 October date comes from the email.

**The email's reassurance is correct and also the trap.** "Nothing changes for
your existing tables" is true, and it makes this easy to file as nothing to do.
The exposure is not production — it is every database built by *replaying* the
migrations: the staging reset, `supabase db reset`, a new project, a preview
branch.

That matters more here than it would elsewhere, because of §6. Anon and
authenticated are deliberately revoked, so `service_role` is the application's
only route into the database. A replayed database whose tables carry no
`service_role` grant is not degraded, it is unusable.

### The gap, measured rather than assumed

Migration 023 grants `all privileges on all tables in schema public to
service_role` — everything existing **at that moment**, nothing after.

Three later tables were granted correctly in their own migrations
(`booking_email_deliveries`, `booking_email_events`, `promo_redemptions`), so
the convention existed and was applied unevenly. **Nine were missed:**
`vehicle_blocks`, `vehicle_change_requests`, and the seven handover tables —
which is the whole of check-out and check-in.

### Neither existing check would have caught it

- `scripts/check-grants.mjs` asserts anon and authenticated hold **nothing**.
  It checks the deny side. A database where `service_role` also holds nothing
  passes it cleanly.
- `check:migration-replay` runs against PGlite with the Supabase roles stubbed,
  so grants there are inert by construction.

### Two things I got wrong on the way

A `grep` for `on all tables in schema public` found nothing and I briefly
believed there was no blanket grant at all. Migration 023 writes it with
**multiple spaces** — `on all tables    in schema public` — which the literal
grep missed and the test's `\s+` did not. Fixed-string searches lie about
formatted SQL.

Then the guard reported **eight** tables and I chased a phantom hole in the
regex for several minutes, because the ninth was real and vitest had simply
truncated the assertion message. Reading the tool's output as complete when it
was elided. The count was right the first time.

### The guard that caught me

`lib/governanceWiring.test.ts` failed on my own documentation: I cited the
runbook as "§14" inside `AGENTS.md`, where that symbol is reserved for
`DEFINING-STATEMENTS.md` sections and every one is checked to resolve. Reworded
to name the section in words, with a note saying why.
