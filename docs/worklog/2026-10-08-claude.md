## The alert path fired, four days after it was fixed

Tasos asked whether the Telegram alert is all set. Three of its four behaviours
were already proven by use: it fires on a real difference (four times), it stays
silent when clean (three times, including last night's 05:51 UTC scheduled run),
and it carries a headline, a counts line and a run URL.

**The fourth had never fired.** On 4 October the condition was widened to
`failure() || steps.compare.outcome == 'failure'` so that a missing secret or a
failed production query would alert rather than skip — and nothing failed early
afterwards, so the fix sat configured and unexercised for four days. That is
exactly the criticism Codex made of `pgaudit`, applied to my own work, and I only
noticed because he had just made it.

`simulate_early_failure` is now a dispatch input: it exits the read step **before
connecting to anything**, so the job fails where a real early failure would with
no production access. Run 37783295976: step 6 `failure`, **step 12 "Tell someone"
`success`** — it ran, where before the fix it would have been skipped — step 13
correctly skipped because no comparison happened.

**A permanent facility, not a throwaway branch**, and that choice is the finding:
the path went unfired for four days because testing it required making a branch
nobody wanted to make. A test that needs a detour does not get run.

## What the alert still cannot tell you

A healthy night and a dead cron are indistinguishable. Last night's silence means
"nothing wrong"; a disabled schedule, a revoked secret or a deleted workflow
would also be silent. **W43**, the heartbeat, is still unbuilt — and the cron now
has five consistent readings of lateness (5h30m, 5h14m, 5h59m, 5h34m, 5h41m), so
"no report by morning" carries no information at all.
