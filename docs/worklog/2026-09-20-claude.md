## Audited all thirteen principles against the code

Loading them exposed §10's stale price within minutes, which argued for checking
the rest deliberately rather than finding them one at a time by accident. Six
are factually checkable; the other seven are process or design judgement.

**Three were wrong. One suspected fault was not.**

**§5 was stale and actively dangerous.** It said *"All price calculation happens
client-side in the booking form. The API formats and emails the values it is
given and never recalculates them."* `app/api/quote/route.ts:301` is headed
"Server-side verification — recalculate independently from DB" and computes
`serverVehicleSubtotal`, `serverTotal`, `serverDeposit`, `serverBalanceDue`. The
client's deposit is bound to `_clientDeposit` and discarded.
`docs/HANDOFF-H1.md` §7 already said *"the server's pricing always wins."*

Worse than an inaccuracy: §5 named the server implementation as the thing to
avoid — "no second implementation to drift out of step". An agent following it
faithfully would delete the recalculation, which is the **tamper-resistance
control** against a crafted request naming an expensive model at a cheap price.
Four tests in `lib/quoteTamperResistance.test.ts` hold it there. Rewritten to
describe what is actually true: one module, two callers, server authoritative.

**§6 was overstated.** *"Tables are never granted to the anonymous role"* —
migration 023 deliberately grants `select` on `rates` and `extras_config`,
because the public form cannot price a rental without them and neither holds a
customer record. An absolute the codebase knowingly breaks is worse than a
precise rule: an agent correcting the code toward it revokes the grants and
breaks public booking. Narrowed, and the grant/policy distinction spelled out —
`001_baseline.sql` creates several policies `to anon` that are inert because the
grant was revoked, which reads like exposure and is not.

**§1 is wrong and I did not fix it.** It claims *"In practice: sources at
~1600px"*. Measured: `fiat-panda.jpg` 300×185, `giant-bike.jpg` 516×387,
`hero-zakynthos.jpg` 1200×800. Correcting the document is the option that
silently accepts worse photographs, so it is **W18** for Tasos: re-source the
images, or lower the stated standard. Not an agent's call.

**§4 checked out.** An early grep suggested `flight_number` was collected but
not stored — a defect §4 names explicitly. It searched only `001_baseline.sql`;
migration 007 adds the column to both `quotes` and `reservations`. No finding,
and worth recording that the false alarm came from searching one file instead of
the schema.

§2, §3 and §7–§13 show no contradiction with the code.

**The pattern across §1, §5, §6 and §10 is the same:** each stated something
absolutely or numerically, the code diverged for good reasons, and nobody
noticed because nothing read the file. They were harmless while unread. They
became live the moment CLAUDE.md began importing them — which is the argument
for the import, not against it.

### A hazard found while waiting: a cancelled check is not a passing check

PR #131's **End-to-end against staging** check came back `cancelled`, not
`failure` and not `success`. The cause is structural, not a flake: that job
declares `concurrency: { group: anadyon-staging-e2e, cancel-in-progress: false }`
so that two runs never touch shared staging at once, and GitHub keeps only
**one** run pending per group — a third arrival cancels the one already queued.
With two pull requests open at the same time, the earlier one's E2E is cancelled
by the later one's.

That is working as designed for staging safety, but it produces a check that is
grey rather than red while the PR still reads as "not failing". Per §8 and the
verification rule, a cancelled check is **not run**, never passed. Recorded on
`OPEN-ITEMS.md`.

### The queue's own load exposed a durable bug in the end-to-end rig

`#133`'s staging end-to-end came back **429** on `replays an identical
submission idempotently`, against a diff consisting of one workflow file the
suite never touches. Not a flake, and the arithmetic settles it.

`lib/rateLimit.ts` counts in the **database**, deliberately — its comment
explains that a per-process Map was wiped by every cold start, so "the limit
existed in the code without existing in practice". `/api/quote` allows ten per
IP per fifteen minutes. But `tests/e2e/01-quote.e2e.ts` allocates addresses
with `let ipSeq = 0; nextIp = () => \`198.51.100.${++ipSeq}\``, and **`ipSeq`
restarts at 0 every run** — so every run replays the same addresses while the
buckets behind them persist.

Most cases spend one request per address per run and so need ten runs in a
window. The idempotent replay spends **two**, because sending the same
submission twice is the thing it tests, so it needs only **five** — and it is
the only case in the file that does, which is why it was the only one to fail.
Working the queue put six runs through staging inside fifteen minutes. It broke
on the fifth.

**The fix was already in the file.** The flood test below had hit this, written
the diagnosis into its own comment, and cleared the bucket — for its one
attacker address. It was simply never extended. #135 clears the range in phase
1's `beforeAll` and widens phase 1b's clear from the attacker to the range, so
that suite does not depend on another `describe` having run first; that also
covers the innocent-caller address, which was accumulating identically and
would have failed next.

**Stated plainly in the PR:** a single green run does not prove this fix,
because the buckets decay after fifteen minutes and a pass cannot be told apart
from having waited. What it removes is the dependence on run history.

### #87 re-examined: the blocker is bigger, and there is a move I had missed

Asked for more detail on #87, and two things in my first assessment were wrong
enough to correct on the PR itself.

**The cause is not a version range.** I had reported `typescript-eslint`
capping at `<6.1.0`. That is the symptom. TypeScript 7.0 is the native Go port
and **ships without a programmatic API at all** — so typescript-eslint, Volar
and Angular's template checking are all locked out, not just us. Microsoft
promises a new and different API in **7.1**.

**And "it becomes mergeable on its own when upstream moves" was too
optimistic.** typescript-eslint#10940 has no milestone and no target version.
Its blockers include ESLint not supporting asynchronous parsers, which matters
because the port would be reached over WASM or native bindings; the maintainers
call the port "many months away from being stable" and say it will not be the
primary TypeScript for another one or two major releases. #87 is dormant, not
imminent. Keep it open.

**What I had missed is that there is a move available now.** `typescript@6.0.3`
is stable and sits inside typescript-eslint's supported range. Tested against
`main` rather than argued: typecheck clean, **0 lint errors** with the same 24
pre-existing warnings, **101 files / 1072 tests**. Nothing trips on 6.0's
changed defaults, because `tsconfig.json` already sets `strict`,
`module: esnext` and `moduleResolution: bundler` explicitly — the defaults 6.0
changed were never being relied on. 6.0 is also the staging post for 7, which
turns 6.0's deprecations into hard errors.

Working copy restored to 5.9.3; nothing staged or pushed. **Raised rather than
built**, per `AGENTS.md` — recorded as **R8**.
