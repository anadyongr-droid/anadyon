## What was decided, and why

**Two positions in the check order are load-bearing, and each has a test that
fails when the control is *moved* rather than removed.**

- **The kill switch runs before authentication.** A switch checked after
  authentication cannot stop an attacker holding a valid session, which is the
  case it exists for. It is also the cheapest check, so correctness costs
  nothing here.
- **The rate limit runs before the idempotency claim.** A refused request must
  not spend a key; if it did, the user's retry — after fixing nothing, because
  there was nothing wrong with the message — would come back "already settled"
  and they would never see the real reason.

Both were proved by breaking them, not by reading the code. Moving the kill
switch to after the send fails `refuses, and NOTHING was sent` with
`expected [ { sender: ... } ] to deeply equal []`. Moving the rate limit to
after the claim fails `does not consume the idempotency key when refusing` with
`expected 409 to be 200`.

**A thrown Zoho client releases the key rather than settling it** — a transport
failure is not a verdict on the message, so a retry must be allowed to send.
**The error string the caller receives is fixed**, so no upstream text, and
therefore no token or internal hostname, can reach it. **The audit row stores
`subjectLength`, not the subject.**

**`submitCorporateSend` never falls back to Gmail's own Send.** A failure that
quietly sends through Google is the precise defect this whole service exists to
remove, so the extension surfaces the failure instead of hiding it.

## The incident: four finished files lost, and recovered by luck

Yesterday's Stage 1 was built in four increments. The first was committed and
pushed. The next three — `store.ts`, `relay.ts`, `relay.test.ts` and the four
extension files, 716 lines with 62 passing tests behind them — were written,
tested, and **left in the working copy to be committed together at the end of
the batch**. The container was then reclaimed, and a new session opened on a
fresh clone of `main` with none of it: no stash, no reflog entry, no remote
branch.

They were recovered from the **session transcript**, which stores each tool call
including the heredocs that wrote the files, and which happened still to be on
disk. Replaying the four `Bash` commands whose input mentioned the service
restored them byte-for-byte.

**That is a usable recovery route and worth knowing. It is not a safeguard.**
Nothing promises the transcript outlives the container. The rule that follows is
in [`ENGINEERING-SAFETY-NET.md`](../ENGINEERING-SAFETY-NET.md): commit each
increment when its tests go green and push it, rather than batching the commit
to the end. `DEFINING-STATEMENTS.md` §11 already says *"unpushed branches are
not a handover"* — the loss here was that same sentence applied to the session's
own next hour rather than to the next agent.

**One thing did work.** Because the recovered tests had been proved against
deliberate breaks in a *different* working copy, both ordering breaks were
re-applied and re-watched to fail in the restored one before anything was
committed. A test recovered from a transcript has the standing of a test
somebody else wrote: it is not proved here until it has failed here. Both
reproduced the original failures exactly, so the recovery is now a checked fact
rather than an assumption about a replayed heredoc.

## Second pass: Stage 1 finished, A to Z

Tasos asked for the whole of it and then for Codex to review. Four pieces, each
committed and pushed when its tests went green — which is the rule the morning's
incident produced, applied the same day.

**`lib/zohoApi.ts` — the real client** (`0996670`). Written against Zoho's
published pages, read today. The send call, the body fields, the attachment
upload step, the refresh grant and the European accounts host are all quoted in
the file's header with what each page did and did not say.

The host is not compiled in: Zoho's multi-data-centre page says the token
response's `api_domain` is where requests go, so the client reads it and
**refuses to send if it is absent**. A guessed host is a different data centre —
a 404 at best, somebody else's tenancy at worst.

**Three things the documentation does not say, and the client refuses each
rather than guessing.** This is the part worth reading twice, because two of
them are answers to §17 that the proposal assumed would come back "yes":

- **more than one address per recipient field is undocumented.** Every published
  sample passes one and the field is described in the singular. A comma-joined
  list read as one malformed address, or as the first only, delivers to fewer
  people than the sender believes and says nothing.
- **there is no documented field for `In-Reply-To` or `References`.** So §17's
  threading question has an answer and it is *"not through this endpoint"*.
  Dropping them would send a reply that starts a new thread in the customer's
  mailbox, which is a customer-visible change and so not an agent's to make
  quietly (§13).
- **nothing documents whether a copy reaches Sent**, so `savedToSent` reports
  `false` meaning *not established*, never *known absent*.

`NOTHING_PROVEN` is the default capability set, every flag false, so enabling one
is a deliberate act with a name that shows up in a diff.

Only a 500 and a thrown transport are retryable: a 400 retried is a 400 again
and a 401 against the same token is a 401 again, and retrying either spends the
idempotency key for nothing while the office waits. **A 200 with an unreadable
body is a send**, not a failure — Zoho does not publish the success envelope, so
the absence of an identifier yields `unidentified:<key>` rather than a released
key and a duplicate message.

**`lib/http.ts` — the transport** (`f5ec75d`). It decides only whether a request
is well-formed enough to be a request; it decides nothing about whether a
message may be sent. The origin check runs before the method is looked at, so a
stranger's preflight learns nothing about which methods exist. No wildcard, and
the default allowlist is empty, which is correct before an extension id exists.
`Content-Type: application/json` is required — a control, not taste: a
form-encoded post is how a cross-site request arrives, and requiring JSON forces
the preflight that lets the origin check run. The body is capped **before**
parsing and measured in UTF-8 bytes, because a character count under-reports
Greek threefold. The token comes from `Authorization: Bearer` and nowhere else;
a `?token=` form would reach access logs and browser history, and a test asserts
it is refused.

**`lib/reconcile.ts` — the HIGH 2 detector** (`5ce4f2a`). The review's objection
was never that Auto BCC might fail; it was that verifying it once at pilot time
is the mistake this project has made five times. So the rule the module is built
around is that **a comparison with nothing in it is never `ok`** — it is
`inconclusive`, and `ok` requires at least one send matched on both sides. A
failed listing is not an empty mailbox: `Listing` is a union, so a caller cannot
pass `[]` to mean "we could not ask". Divergence outranks inconclusiveness. And
the canary is what makes a quiet period checkable, since `ok` needs a matched
send and a week of no office mail would otherwise never confirm the path.

The correlation identifier is **named as unresolved**: Zoho's `messageId` is in
the audit row but its appearance in a Sent listing is unverified; the RFC
`Message-ID` is neither accepted nor returned by the documented API; a header
the relay sets itself is the robust answer and is unavailable for the same
reason `In-Reply-To` is. Our own privacy decision costs the easy key — the audit
row stores `subjectLength`, not the subject.

**`extension/` — the relay call** (`a1f3082`). The review's finding 6 was right
that everything in the extension was a promise. The logic moved into two
injected modules so the promises became properties: `credentials: "omit"` so a
signed-in Google session cannot be carried to the relay, `redirect: "error"` so
the token cannot be replayed to another host, nothing from a thrown `fetch`
reaching the Gmail page, and `sent: false` for every failure shape — 400, 401,
429, 500, 503 and a thrown messenger. The manifest is asserted as well, so a
widened permission fails a test rather than depending on a reviewer noticing.

## Three defects in my own Stage 1, found while extending it

None was found by a failing test. All three are fixed, and the first two had
already been pushed.

1. **A cross-user read in the idempotency store.** `lookup` took a key and
   nothing else, so `handleStatus` let any authenticated user read any key's
   outcome — whether it was sent, and Zoho's identifier for it. `claim` and
   `lookup` now take the owner, and the owner is part of the operation rather
   than a filter on its result, because the three claim states each carry
   information: another user's key answers `in_flight`, which refuses while
   saying nothing. Filtering afterwards would mean having already read someone
   else's outcome.
2. **`content.js` could not have run.** It had top-level `export` statements,
   and an MV3 content script declared in `content_scripts` is not an ES module.
   Either keyword is a syntax error in the page: the script never runs, the
   action never appears, and nothing shows in the extension's log because there
   was no script to log from. A test now parses it as a classic script.
3. **A link to a document that is not on this branch.** The service README
   pointed at `docs/GMAIL-ZOHO-OFFICE-MAIL-PROPOSAL.md` as though PR #241 had
   merged. It has not. Corrected to say where the proposal lives.

The first two are the kind this project keeps producing: a control that is
present and inert, and an instrument that cannot report its own absence. Both
now have tests that fail when the control is *moved or removed* rather than
merely when the behaviour is wrong.

## What is left, and who holds it

**Not code:** the service must be extracted to its own repository and credential
boundary before Stage 2, which §6.2 requires and this directory does not
satisfy.

**Code, and Stage 2 by design:** the Gmail DOM selectors — the only remaining
promise — and a build step inlining the extension modules into `content.js`.
Attachment upload is blocked by our own request type carrying a byte count
rather than the bytes.

**Tasos's, and now specific rather than "verify sending".** With a
non-production address and an OAuth client, four observations settle the design:
send to **two** recipients and confirm both received it; send a reply and see
whether the thread holds, and if not whether Zoho accepts any header field for
it; look in **Sent** and record whether the copy is complete; and note whether
the response's **`messageId`** appears in a Sent listing — that is the
reconciliation key, and nothing else available settles it.

**One operational trap**, written down because the failure appears months later
and looks like something else: Zoho allows a user twenty refresh tokens and
silently deletes the oldest when a twenty-first is issued, *including one still
in use*. Re-authorising repeatedly while setting this up can revoke the
deployment's own token with no error at the time.

**And E39 is still the open decision.** Stage 1 being finished does not settle
it. The costing is unchanged, the bridge is still the most expensive option once
maintenance is counted, and it is still the only one that adds a component with
read access to the administrative mailbox. What today changes is that the
engineering side of the comparison is now measured rather than estimated.
