## What was decided, and why

- **Check the artefact, not the job that was supposed to produce it.** Three
  pieces of evidence about the backups already existed and all three were
  circumstantial: 30 green runs (the evidence that lied here before), one
  night's log, and the prune line showing the thirty-first object deleted.
  **A count is not a distribution** — thirty-one objects spanning a month is
  equally consistent with a fortnight of doubles and a fortnight of nothing.
  Same family as reading `switch_rows 1` as an identity on 4 October.
- **An alert may state what the run established and what to do about it. It may
  not state what the failure might mean.** The drill's first alert said "the
  backups may be unrecoverable" during a run that had restored 1,742 of 1,744
  rows. The alarm was real and the diagnosis was invented by the wording.
  Tasos asked whether it was valid information, which is how it was found.
  `scripts/restore-drill-alert.mjs` now keeps three cases apart; restoring the
  original wording fails six of nine tests.
- **The restore classification draws its line at the schema.** `public` is
  ours and never exempt; `auth`, `storage`, `realtime`, `graphql`, `vault` and
  `extensions` are the platform's and a plain Postgres cannot host them.
  Widening it to any schema fails three tests, run deliberately before trusting
  it. Tolerating wholesale would have buried
  `relation "public.reservations" does not exist` among two dozen platform lines.
- **`postgres:17` for the restore target, tagged rather than digest-pinned.**
  Production is 17.6; the migration replay is PGlite 18 (W49). An action is code
  running with the job's secrets and is pinned by SHA; this is a database the
  job throws data into and destroys, so freezing its security patches is the
  wrong trade.
- **Platform roles for the restore live in their own file**, not in
  `pgliteSupabaseStubs.mjs`. That file is the migration-replay gate's fixture
  and its own header explains why it must not drift.

## What I got wrong

- **Migration 050, written and withdrawn.** Views were outside the grant model
  — 046 and the test both match `create table`, the fingerprint filters
  `relkind in ('r','p')` — and `vehicle_open_damage` is a view created after
  023's blanket grant. Production (run **39493105577**) showed `service_role`
  holding all eight privileges with no migration apparently granting them, so a
  migration was written. **The view's own migration grants it on line 55.**
  The trap: production holds eight privileges where the migration grants one,
  so *more in production than in the repository* read like *none in the
  repository* — the platform had added seven on top of our `select`. §8 says
  verify; it does not say one reading cannot be misread. The grep for a grant
  naming the view, in the view's own file, should have been first.
- **I committed the runbook as zero bytes.**
  `open(p, "w").write(open(p).read().replace(...))` truncates at open time,
  before the read in its own argument list, so 1,505 lines became nothing.
  Restored from `07d1400` and re-diffed against it: +22/−1. Caught by checking
  the result rather than assuming the write worked.
- **I fabricated an image digest** for the `postgres:17` service container in
  the first draft of `restore-drill.yml`, and corrected it to a tag before
  pushing. A digest I cannot verify is not a pin, it is a guess that looks like
  one.
- **A test of my own was wrong, not the code.** `restoreDrillAlert` asserted
  the message must not match `/lost backup/`, which the deliberate reassurance
  "this is not a lost backup" matches. Fixed the assertion to match the claim
  rather than the words.
