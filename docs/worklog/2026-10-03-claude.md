## The design document and the independent-review brief

Two new files, and the split between them is the point.

**[`docs/AGENT-ACCESS-AND-MONITORING.md`](AGENT-ACCESS-AND-MONITORING.md)** — our
design, indexed from `docs/README.md`. It names three failure paths (CLI, the
agent's own tools, and **the browser inside a logged-in session**), labels every
control **enforced** or **advisory** rather than listing them flat, and states what
it does not cover with the residual risk as a number: **same-day detection of a
browser action against production does not exist, up to 24 hours.**

**Four open questions, recorded as open, two of them flaws in my own design:**

- **Q1** — the tier-2 collector credential sits on the machine the agent controls,
  so the agent can read it and therefore forge or suppress entries. Possibly not
  solvable on one machine, in which case tier 2's honest claim is "detects mistakes",
  not "detects an adversary".
- **Q2** — fail-open versus fail-closed when the collector is unreachable. Neither
  answer is good, and the obvious third (buffer locally) is Q1 again.
- **Q3** — **tier 3's central invariant is wrong for this project.** "Every
  production change must be explainable by a merge commit" would fire on every
  hand-applied migration, because `AGENTS.md` forbids an agent applying one. An alarm
  that cries wolf monthly gets muted, and a muted alarm is worse than none because it
  still looks present.
- **Q4** — the distribution unit for reusing this across projects has no shape.

**[`docs/agent-controls/fable-brief.md`](agent-controls/fable-brief.md)** — the
brief, deliberately containing **no part of our design**. It carries every platform
fact we verified, each marked verified or unverified, plus three facts we explicitly
have not checked and that the reviewer should not inherit — including whether Codex's
hooks fire for browser actions at all, which would change the design materially if
they do.

**The operational trap, and it is the reason the brief leads with it.** The brief
must be pasted into a chat with **no repository attached**. This repository contains
the design document; a reviewer that can read the repo will find it and hand back our
architecture with improvements rather than an independent one. **That failure is
silent** — it still looks like a review. It is the same shape as the one that already
cost us this week, when the 2 October audit inherited a wrong vehicle count because it
trusted our document rather than recounting the table beside it.

**Two recommendations on how to run it**, both in the brief: derive first and diff
second, because agreement only means something if the second design was reached
independently; and give the adversarial pass to **Codex rather than another Claude
model**, since two models of the same family share training and therefore blind

record; how?"* — because "assess this architecture" produces praise and "defeat this"
produces findings.

## The adversarial pass found that my central claim was false

**Codex's finding, verified by me before accepting it.** The Codex permissions
documentation states, verbatim: *"The network proxy only filters traffic from local
commands that run inside the sandbox"*, and lists Browser and Computer Use among
what it does **not** control. So `[features.network_proxy] deny` does not reach the
browser, and the claim that it was *"the only layer that reaches the browser"* —
repeated in six places including E22, where it was the stated reason the item was the
priority — is wrong.

**How I made the error, which matters more than the error.** It rested on one
sentence from a different page: *"browser tools separately check managed network
denies."* I read that as *"and browser tools also check network denies."* It says the
opposite. **"Separately"** means browser tools consult a different mechanism, and
**"managed"** means the administrator-managed requirements file, not a user's
`config.toml`. Both load-bearing words were inside the quotation I pasted myself, and
I read past both — then built a priority ordering on top of it and told Tasos it was
the most important thing to do.

**The document contradicted itself and nothing caught it.** §6 already said *"same-day
detection of P3 does not exist in this design."* §3 said the Codex deny covered P3.
One had to be wrong and the pessimistic one was right. **This is the same failure
shape as the insurance count corrected yesterday** — prose in one section disagreeing
with a statement in another — twice in two days, which makes it my pattern rather than
an accident. No test catches a document contradicting itself, and I do not think one
cheaply can; the control is review, which is exactly what found it.

**Corrected in six places**, with the mechanism recorded in each: the design doc's
tier table, runbook §16, the paste-ready toml's rationale, E22's justification and
priority, question 2 of the adversarial prompt (now marked answered), and this
worklog, struck rather than rewritten per §11.

**What it changes.** **P3 has no project-specific enforcement under a single owner
account** — which is now the agreed position of all three readings, mine included.
Pasting the Codex deny is still worth doing because it genuinely bounds Codex's shell
commands, but it is no longer the priority and the reason given for prioritising it

permissions page I read, so it is recorded as **unverified**. Even if it exists,
Codex's own argument stands: an origin block cannot separate production from staging
when both dashboards are paths under one host.
