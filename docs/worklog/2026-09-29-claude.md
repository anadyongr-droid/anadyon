## Two defects, both found from the live screen rather than from the code

**Motorbike rates were collected all along and could never be mapped.** The mapping
screen renders a category with no group code as `"?"`, and the save sent that string back
as `.eq("car_group", "?")`. **SQL equality never matches NULL**, so the update affected no
rows: the category could be mapped, saved, reported as *"Saved — 0 observations
classified"*, and silently never appear. Nothing failed; the count was zero and a zero
reads like "nothing to do". Scooters were the visible casualty because a car-group code is
a car concept — EzCar returns two-wheelers from a different endpoint where the field does
not exist. **Three of the four importers can write null**, so Faros and CarRentals rows
can land in the same hole. Now matched with `.is("car_group", null)`.

**Months were out of calendar order.** The loop iterates `rates` on the outside and months
on the inside, and `rates` is fetched with `select("*")` and **no `ORDER BY`** — so
Postgres returns the season rows in any order, and a group with three seasons emits its
months grouped by season. The months array *was* sorted, which is exactly why this was
easy to miss: the sort was real, just applied one loop too far in.

- **The Telegram check reports the token and the chat id differently.** A missing token is
  silence: `sendTelegram` returns without queuing or logging. A missing chat id is *not* a
  failure — messages still go out, to a hardcoded fallback group. "Delivering somewhere
  unintended" must not read like "not delivering". The last four digits of the chat id are
  shown; the token never is.

## What was found out about the importers, and is not written down anywhere else

**Navigating away mid-import means three different things.** EzCar writes a cursor every
batch and resumes. Podilatadiko runs only on the call where the pass *completes*, so it is
deferred, not lost. **Faros and CarRentals ingest inside the polling `GET`** — leave the
page and the Apify run finishes server-side with nothing ever fetching the dataset, and
`POST` does not check for a finished-but-uningested run, so pressing the button again
spends the budget a second time. CarRentals runs through residential proxies billed by
traffic. **That fully explains why those two sat at 16 August.** Not yet fixed; proposed.

## What was decided, and why

- **The repricing panel holds no `fetch` at all**, rather than merely not calling PATCH. A
  POST to some other route that happened to write rates would satisfy the narrower rule,
  and §13's protection should not depend on which verb an agent reaches for. The test
  asserts the absence of any network call.
- **`RECOVERABLE_WITHIN_MS` is 24 hours.** Below it, collecting a finished run saves
  something already paid for and the prices still describe roughly today's market. Above
  it, the searched pickup dates are sliding out of the planned window and an unnamed Apify
  dataset is heading for expiry, so paying again buys something better. It is a judgement,
  named as a constant so changing it is one edit.
- **A recovered dataset is dated by Apify's `finishedAt`.** Recording the moment of
  collection would report last night's prices as this morning's — the exact overstatement
  the import log replaced `MAX(scraped_at)` to remove, reintroduced through a different door.
- **The bikes-last ordering was changed even though its original reason was sound.** The
  comment was right that a cursor is an index and reordering invalidates it. The answer was
  to make the cursor able to tell, not to keep the scooters where a partial pass never
  reached them.
- **No motorbike parser was written.** Both remaining candidates need a browser, and this
  sandbox cannot render either page — Playwright's Chromium does not trust the agent
  proxy's CA, and disabling verification is not an option. A parser written against markup
  nobody has seen would pass its own tests, because the tests would come from the same
  guess. §1.6a records what unblocks each instead.
