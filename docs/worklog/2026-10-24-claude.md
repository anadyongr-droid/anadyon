## 1. E6 is closed: the mail certificate is reissued, and my own evidence was wrong

**What happened.** Tasos reported that Papaki had finally answered, five weeks
after the first ticket, claiming they had renewed the mail certificates and
updated PHP. Earlier in the day I had recorded that claim as **unverified**, with
Certificate Transparency as the evidence against it: no certificate issued for
`anadyon.gr` since Vercel's of 18 August.

**The claim was true and my instrument was blind.** Verified through SSL Labs'
own TLS handshake:

```
host: webmail.anadyon.gr   status: READY   grade: A   issues: 0
subject : CN=webmail.anadyon.gr
names   : mail.anadyon.gr, webmail.anadyon.gr
valid   : 2026-10-24 -> 2027-01-22
issuer  : CN=YR2, O=Let's Encrypt, C=US
```

`mail.anadyon.gr` is on it. That is the host the SMTP service answers on, the
component Plesk had been reporting as `Mail access — IMAP, POP, SMTP on
mail.anadyon.gr — Not Secured`, and the reason Gmail's relay had been falling
back to Google since 12 October.

**Why SSL Labs rather than `openssl`.** Ports 587 and 465 are not reachable from
an agent container, and on 443 this session's egress proxy re-terminates TLS, so
`openssl s_client` returns the proxy's certificate instead of the server's — a
limitation already recorded against E6 on 14 September. SSL Labs performs the
handshake on its own network and reports the chain it was served, which makes it
an observation of the server rather than of the path to it.

### The mistake, which is the part worth keeping

The certificate is scoped to `mail.` and `webmail.` **only** — no apex, no `www`,
no wildcard. That is precisely the shape `EMAIL-DELIVERABILITY.md` had spent
three sessions arguing for, on the ground that `anadyon.gr` and `www` resolve to
Vercel and can never satisfy HTTP-01 at Plesk again.

**And it is exactly the shape a CT query on `q=anadyon.gr` cannot see.** The
recommendation and the verification method were in direct conflict, and the
conflict only becomes visible once the recommendation is followed. Nobody caught
it because nobody had followed it yet.

§8 requires an unverifiable claim to be labelled unverified, and it was labelled.
The error is narrower than that and worth naming on its own: **a measurement's
silence was read as a statement about the world.** "CT shows no new certificate"
is a fact about an index. "No new certificate exists" is a fact about a server.
The first implies the second only if the index is known to be complete for the
thing being asked, and it was not.

Written into `EMAIL-DELIVERABILITY.md` with the withdrawal visible rather than
edited away, alongside the two earlier conclusions on this incident that were
also withdrawn ("always broken, merely tolerated"; "a reputation slide, E6 not
implicated"). Three wrong readings on one incident is worth the space: each would
have sent the fix somewhere different.

**For the next certificate question:** query CT for `mail.anadyon.gr` and
`webmail.anadyon.gr` as well as the apex, or skip CT and read the handshake.

### What is proven, what is not, and what unblocked

- **Proven.** TLS on the mail host is valid to 22 January 2027, so Gmail's relay
  no longer fails verification and no longer falls back to sending as Google.
- **Not proven, and deliberately not assumed.** That a reply from
  `customerservice@anadyon.gr` to a Yahoo address now passes DMARC end to end.
  The certificate was the broken link; a chain with one link repaired is a
  repaired link, not a tested chain. **E34 stays open on one send**, which needs
  the mailbox and is therefore Tasos's.
- **E10 (the CAA record) is unblocked.** Its stated precondition was that both
  certificates renew cleanly first, because a CAA record set slightly wrong would
  block issuance for Vercel and Plesk at once. It must authorise **both** issuers,
  read from the live chains rather than assumed.
- **E33 is not closed and needs a sharper question.** "We updated PHP" is not
  "PHP is patched": the fixed releases are 8.2.35 / 8.3.36 / 8.4.27 / 8.5.12, and
  8.1 and older are end of life with no fixed release at all, so an update
  *within* 8.1 leaves the unauthenticated-RCE exposure intact. The question to
  ask is **which version is running**, not whether they updated.

### 3.1 An exact peer pin makes a split bump unsatisfiable (#214 / #215)

`@vitest/coverage-v8` peer-depends on an **exact** vitest version — `4.1.11`
requires `vitest@4.1.11`, `5.0.5` requires `vitest@5.0.5`. So Dependabot's two
pull requests each bumped one half and **neither could ever go green**:

```
npm error Conflicting peer dependency: vitest@4.1.11
npm error   peer vitest@"4.1.11" from @vitest/coverage-v8@4.1.11
```

**The tell is that the failure is at `npm ci`, before a test runs.** Dependabot
opens one pull request per package and cannot combine two, so I pushed the other
half onto #215 and commented on #214 as superseded.

Verified on that branch rather than assumed: clean `npm ci` from an empty
`node_modules`; `verify:fast` green (147 files, 1,728 tests, lint at 0 errors and
the 24 pre-existing warnings); and **`npm run test:coverage` run to completion**,
because a coverage package that installs but cannot instrument would pass
everything above it.

### 3.2 A grouped action bump cannot contain a workflow that did not exist yet (#220)

#220 bumped `actions/setup-node` in four places and was opened on **20 October**.
`restore-drill.yml` was added to the repository **later the same day** with the
old pin. Merging `main` into the branch therefore produced a tree holding two
different SHAs for one action, and `lib/actionPinParity.test.ts` failed naming
the line:

```
.github/workflows/restore-drill.yml:83 actions/setup-node v7.0.0
```

That is the parity test doing exactly what #83 taught us to build it for — a
split pin across one action family once would have run a mismatched CodeQL
bundle with nothing in the repository saying so. I reproduced the failure first,
fixed the one pin, watched the test go red → green, and pushed. #220 then went
green end to end and merged.

**The general rule:** any action pin added to a *new* workflow while a group bump
is open will collide with it. `git grep` the old SHA whenever a grouped action
pull request goes red after a branch update.

### 3.3 A loose peer range hides a plugin that does not support the new major (#170)

eslint 9 → 10 fails the Lint step with **exit code 2** — eslint's fatal
configuration error, not a lint violation:

```
TypeError: Error while loading rule 'react/display-name':
  contextOrFilename.getFilename is not a function
    at …/eslint-config-next/node_modules/eslint-plugin-react/lib/util/version.js:31
```

`context.getFilename()` is one of the context methods ESLint 10 removed. The
caller is `eslint-plugin-react@7.37.5`, vendored inside
`eslint-config-next@16.3.5`:

| package | version | declared eslint support |
|---|---|---|
| `eslint-config-next` | 16.3.5 | `>=9.0.0` |
| └ `eslint-plugin-react` | 7.37.5 | `^3 \| … \| ^9.7` |

The loose range is why npm installs the pair without complaint and why the break
appears only at lint time. **And there is nothing to upgrade to:**
`eslint-plugin-react@latest` is still 7.37.5 with the same ceiling, checked
against the registry today, so no released version supports ESLint 10 and an
`overrides` entry has nothing newer to point at. The only `eslint-config-next`
above ours are `16.5.0-canary.*` prereleases, which are not going on `main` for a
dev-dependency bump.

**Recorded as W63 and the pull request left open as the tracker.** It becomes
mergeable on its own once upstream moves. Saying so is the action; forcing it
would not be.

### 3.4 What the three have in common, and the method that found them

GitHub's check-run annotation carries only `Process completed with exit code N`.
Logs and artifacts are unreachable from an agent container (**W51**), and the
step index in the annotation is not a file line. So the method that works is to
**reproduce the install and the one failing step locally** — `npm ci` from an
empty `node_modules`, then that step alone. All three were found that way in
minutes. Reading the diffs and reasoning about what the new version might break
would have found none of them.

## 4. W62 — a CI concurrency group that cancels queued runs in silence

**Opened today, and it is the explanation for four pull requests sitting
unmergeable with nothing red.**

`ci.yml`'s `e2e-staging` job carries:

```yaml
concurrency:
  group: anadyon-staging-e2e
  cancel-in-progress: false
```

The constant group name is **correct** — the job writes to the shared staging
database and two runs must not overlap. But a constant group is shared across
every branch and pull request, and **GitHub holds only one pending run per
group: when a third arrives, the one already waiting is cancelled.**

With one or two open pull requests this is invisible. With a queue of eleven,
`End-to-end against staging` came back `cancelled` over and over, on diffs that
never touch staging. **A cancelled required check is neither red nor green**, so
the pull request cannot merge and there is no failure to investigate — which
reads exactly like a flake and is not one. I lost time treating it as one before
reading the workflow.

**Worked around** by merging strictly one at a time and re-running the cancelled
job per pull request (`actions/runs/<id>/rerun-failed-jobs`). Slow but reliable.

**Deliberately not fixed, and recorded to be decided.** The three options are a
real trade-off rather than an oversight:

- a per-ref group stops the cancellations but allows two runs to write to one
  staging database, which is what the constant group exists to prevent;
- running it on `main` only and dropping it as a required check removes the
  problem entirely, at the cost of learning about a staging break after merge,
  and needs a branch-protection change;
- keeping it and accepting serial merging, which is fine for three pull requests
  and not for eleven.

Which is right depends on how much the pre-merge staging signal is worth. That
deserves one deliberate decision rather than three silent cancellations, so it is
W62 rather than a change I made quietly in a documentation branch.

### Addendum, 16:25 — #223 landed, and it needed resolving by hand

Dependabot never took the rebase it was asked for, so the conflict was resolved
manually and the detail is worth keeping because the easy resolution is the
wrong one.

**Not by picking sides in the conflict markers.** A lockfile hunk resolved as
"ours" is how a dependency silently reverts while the pull request still claims
to have bumped it. Instead: take `main`'s `package.json`, re-apply this branch's
bumps on top, and regenerate the lockfile from `main`'s rather than merging it
textually.

Three things that surfaced only by doing it that way:

- **One of the ten was already done.** `next` had been bumped to `^16.4.2` on
  `main` by #221 earlier today, so nine of the ten actually moved. A
  side-picking merge would not have revealed that.
- **Two locked above the floor the pull request names** — `resend` 6.33.0 →
  **6.34.1**, `lucide-react` 1.57.0 → **1.61.0** — because the caret ranges
  permit it and a fresh install takes the newest match. That is the normal
  outcome and what any contributor's tree holds, but it is two versions
  Dependabot did not itself test, so it is in the commit message rather than
  left to be found in the lockfile.
- **`main` moved again mid-verification**, when #215 merged, so the whole tree
  was re-merged and re-verified instead of pushing something already stale.
  That is W62's cost showing up as wasted cycles rather than as a failure.
